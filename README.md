# sakuya

QUIC transport implementation for Open Gensokyo Network, administratively supported by Starspun Works.

The repository is at an early stage. It holds parts of a QUIC version 1 implementation and does not yet provide a usable connection. The APIs are experimental and are not stable production APIs.

## Layout

- `crates/sakuya_wire`: wire-level value types (variable-length integers and fields that keep the width of their encoding, connection IDs and their lengths, stateless reset tokens, stream IDs, stream counts, packet numbers and the length of their field, versions, error codes), version-independent packet header interpretation and the headers a sender writes up to the Packet Number field, the cutting of a datagram into its packets (protected packets, and the Retry and Version Negotiation packets that are not), the encryption levels with the frame types that can appear in each, QUIC version 1 frames and transport parameters. The crate root holds what every QUIC version shares, the frame sets that compose the frames of version 1 with those of extensions, and the sets of parameters keyed by ID that compose parameter types in the same way; everything else of RFC 9000 is in its `v1` module. Each transport parameter is a type of its own, and the transport parameters of an endpoint are a slot for each type of the parts it uses, with the parameters no type claims kept as unknown ones. The DATAGRAM frame of RFC 9221 and the RESET_STREAM_AT frame of the reliable stream reset draft are extensions, each with its transport parameter in a module behind a feature of the same name (`datagram`, `reset_stream_at`), off by default; a frame set without an extension reads its Frame Types as unknown, and transport parameters without it keep its parameter as an unknown one. Every wire format is read and written as `nitori_call` operations, which also run synchronously on byte slices and `Bytes`; payload fields are chunks of the source, without copying. A frame value states every detail of its encoding (the width of each variable-length integer, which optional fields are present, the raw fields of ACK), so reading a frame and writing it again reproduces its bytes; the Frame Type must use its shortest encoding.
- `crates/sakuya_packet_protection`: packet protection primitives from RFC 9001: Initial secrets, key derivation, header protection, AEAD packet protection, truncation of packet numbers in the Packet Number field and the Retry integrity tag, behind a cryptographic backend trait with a `ring` implementation (the default `ring` feature). It depends on `sakuya_wire` for the connection IDs and packet numbers it takes.
- `crates/sakuya_link`: the identities of link bindings (`BindingId`) and links (`LinkId`), unique within a process, where each link identity also records the identity of the link binding that produced it.
- `crates/sakuya_datagram_routing`: routing of received UDP datagrams to registered deliverers (a shared-bucket index keyed by connection ID or link binding, registrations revoked by RAII handles, frozen candidate groups, non-inline reflow of unclaimed datagrams, re-examination and publication of new Initial receivers, and a hook for stateless reset detection), and the claim mechanism by which several candidates compete for one datagram.
- `crates/sakuya_stream`: per-stream send and receive components. The send direction has connection-level credit reservation and commitment, a send buffer contract with an implementation keyed by stream offset, and a stream sender with its flow-control and termination policies; the receive direction has a receive buffer contract with a fragment-map implementation, connection-level receive accounting, and a stream receiver with reads, local stop requests and policy-driven delivery boundaries. The stream receiver is generic over the reset facts it keeps: by default it takes the resets of RFC 9000, and the `reset_stream_at` feature, off by default, adds a module of the same name with the facts and frame methods of the reliable stream reset draft (RESET_STREAM_AT) for the receive direction; the send direction is not yet split this way. Both directions are synchronous cores; waiting and async adapters are not implemented.
- `crates/sakuya_tls`: the TLS 1.3 handshake layer for QUIC. It has the TLS code points (cipher suites with their hash and AEAD, extension types, handshake types, alert descriptions, protocol versions), the handshake messages (ClientHello, ServerHello and HelloRetryRequest, EncryptedExtensions, CertificateRequest, Certificate with X.509 certificates or a raw public key, CertificateVerify, Finished, NewSessionTicket, and the message_hash message of the transcript) with their extensions, and the collection of one whole handshake message from the bytes of an encryption level, under a limit for each message type. Messages are read from the bytes of one whole message as `nitori_call` operations, with variable-length fields as chunks of those bytes, and written back byte for byte; a recognized extension in a message that may not carry it is rejected, unknown extensions are kept, and every read failure names the TLS alert it calls for. The transcript and key schedule form one chain of values that move, with the role of a server or a client as a type parameter: each step consumes the one before, so the Handshake traffic secrets need the ServerHello, the 1-RTT secrets need the server's Finished, and a client reads the server's Finished only after the server has authenticated with a certificate or with the PSK it accepted. The chain derives the traffic secrets for packet protection, the Finished messages, PSK binders, 0-RTT secrets, the exporter and the PSKs of tickets, over a backend with the capabilities of `nitori_crypto`. The handshake engines of a server and of a client are `nitori_call` operations that own the backend and their role's capabilities, read and write the CRYPTO bytes of the current encryption level through receivers the connection lends on every poll, ask the connection for transport parameters through synchronous methods, and yield the traffic secrets and the completion of the handshake, with its exporter, as they become available; a server holds back the client's 1-RTT secret until it has verified the client's Finished, and admits 0-RTT only when the handshake, the connection and its ticket policy all agree. The engines do not yet open encrypted ClientHello layers or authenticate clients with certificates, and there is no QUIC client connection yet to drive the client engine.

Byte IO, the call mechanism, process-unique identities and cryptographic capabilities come from [nitori](https://github.com/opengensokyonet/nitori).

## Development

Install [rustup](https://rustup.rs/). The repository pins `nightly-2026-11-03` with rustfmt and Clippy in `rust-toolchain.toml`; run commands from the repository root so rustup selects this toolchain. Nightly language features are required. Packages remain unpublished (`publish = false`).

`nitori_call`, `nitori_crypto`, `nitori_id` and `nitori_io` are Git dependencies on [nitori](https://github.com/opengensokyonet/nitori), and `snafu` is a Git dependency, each pinned to a specific commit in `Cargo.toml`; Cargo fetches them automatically. The tests of `sakuya_tls` also use `nitori_crypto_aws_lc`, which builds aws-lc-rs from C sources and needs a C compiler and CMake.

From the repository root:

```sh
cargo fmt --all --check
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo clippy --locked --workspace --all-targets --all-features -- -D warnings
cargo test --locked --workspace --all-targets
cargo test --locked --workspace --all-targets --all-features
cargo test --locked --workspace --doc
```

For development against local checkouts of nitori or SNAFU, an ignored `.cargo/config.toml` may patch their Git sources to local paths under `[patch."https://github.com/opengensokyonet/nitori"]` and `[patch."https://github.com/opengensokyonet/snafu"]`. Keep that configuration and the resulting lockfile changes out of commits; the committed lockfile records the public sources.
